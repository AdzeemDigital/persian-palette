# معیارهای انتشار (Release Gates)

این سند برای چهار حکم مستقل، معیار صریح تعیین می‌کند. این حکم‌ها **با هم میانگین گرفته نمی‌شوند**، و ردشدن یک دروازه با پاس‌شدن دروازهٔ دیگر جبران نمی‌شود. هر معیار باید یک شاهد قابل بازتولید داشته باشد: لاگ، commit، آزمون یا سند. وضعیت فعلی هر حکم در `AUDIT_REPORT.fa.md` آمده است.

سه سطح حکم:
- `ready`: همهٔ معیارهای الزامی برآورده شده‌اند.
- `ready-with-explicit-limitations`: معیارهای الزامی برآورده شده‌اند، ولی بعضی معیارهای «محدودکننده» اجرا نشده‌اند. در این حالت ادعای عمومی باید دقیقاً به دامنهٔ آزموده‌شده محدود شود و محدودیت‌ها کنار همان قابلیت (نه فقط در README) نوشته شوند.
- `not-ready`: دست‌کم یک معیار الزامی برآورده نشده است، یا یک یافتهٔ Critical/High مرتبط بدون حل مستند باقی مانده است.

---

## حکم ۱: جعبه‌ابزار دیجیتال طراحی و رنگ

**الزامی**
1. `npm ci`، `npm run check`، `npm run pack:core` و `npm run verify:package` روی commit نامزد و در CI (Ubuntu و Windows، Node 22 و 24) سبز باشند.
2. محاسبات اصلی (Oklab، HCT، APCA، WCAG ratio، CIELAB) در تلرانس مستند با یک اوراکل مستقل تطابق داشته باشند. معیار: خروجی `evidence/A02-color/oracle-comparison.mjs` یا آزمون معادل.
3. هیچ ورودی نامعتبری بی‌صدا با مقدار دیگری جایگزین نشود، نه در کتابخانه و نه در UI (MSR-API-004).
4. نام‌ها و توضیح‌های API عمومی رفتار را درست توصیف کنند. «spectral»، «pigment» و «physical» فقط با توصیف دقیقِ «نمایشی/دیجیتال» به کار روند (MSR-SCI-002).
5. خروجی‌ها روی ورودی‌های نام‌گذاری نامعمول، خروجی شکسته یا قابل تزریق تولید نکنند (یافته‌های W3).
6. هیچ یافتهٔ Critical/High حل‌نشده‌ای در دامنهٔ فنی نمانده باشد.

**محدودکننده** (اجرانشدن فقط ادعای مربوط را محدود می‌کند)
- کامپایل Swift و Kotlin در پروژهٔ حداقلی. اگر اجرا نشده باشد، ادعا «کد تولیدی، کامپایل‌نشده» باشد.
- import در Figma یا Tokens Studio. اگر اجرا نشده باشد، ادعا «قالب تبادل پروژه» باشد.
- مصرف واقعی Tailwind v4.

## حکم ۲: مرجع فرهنگی قابل استناد (در دامنهٔ مشخص)

**الزامی**
1. **در محل استفاده** (UI، tooltip، خروجی و README) چهار نوع محتوا از هم جدا باشند: ادعای تاریخی مستند با ارجاع، عدم قطعیت، تصویرسازی یا مدل نمایشی، و مقدار دیجیتال انتخاب طراح. معیار: هیچ برچسبی مثل «Primary source documented» روی رکورد تأییدنشده نباشد (MSR-I18N-002).
2. هر ارجاع دقیقاً از همان ادعایی پشتیبانی کند که به آن نسبت داده شده است: محل دقیق (صفحه، شیء، شناسه)، تاریخ دسترسی و نوع منبع ثبت شده باشد، و یک بازبین منبع را خوانده باشد (`CULTURAL_CLAIMS.csv`).
3. ادعاهای بی‌پشتوانهٔ اصالت («اصیل»، «استاندارد جهانی»، «authentic»، «authenticated»)، اندازه‌گیری («physics»، «spectral reflectance» بدون قید) و تأیید نهادی حذف، اصلاح یا صراحتاً مشروط شده باشند. این شامل دارایی‌های توزیع‌شده (ZIP) هم هست، یا دست‌کم باید اصلاحیهٔ عمومی داشته باشند.
4. ادعاهای «contradicted» در ledger (مثلاً طول موج غالب برای رنگ‌های غیرطیفی) اصلاح یا حذف شده باشند.
5. تعارض‌های مختصات یا حل شده باشند (با منبع)، یا در UI به‌عنوان تعارض و بدون انتخاب پیش‌فرض نمایش داده شوند.
6. شناسهٔ پایدار، نسخه، راهنمای استناد (`CITATION.cff` بدون DOI ساختگی)، مجوز داده و سابقهٔ اصلاحات وجود داشته باشد.
7. دامنهٔ مرجع صریح باشد. مثال: «این پروژه مرجع نام‌ها و مقادیر دیجیتال خود است، نه مرجع تاریخ هنر».

**یادداشت:** ابزار طراحی صادقی که یادداشت‌هایش را «الهام/تفسیر ویرایشی» برچسب زده باشد، برای حکم ۱ به قطعیت تاریخی نیاز ندارد. حکم ۲ فقط برای ادعای «مرجع قابل استناد» است.

## حکم ۳: برنامهٔ دوزبانهٔ دسترس‌پذیر (در دامنهٔ آزموده‌شده)

**الزامی**
1. اسکن خودکار axe (برچسب‌های WCAG 2.0/2.1/2.2 در سطح A و AA) روی هر دو نسخه، هر دو تم و دیالوگ‌های اصلی، بدون نقض جدی یا بحرانیِ حل‌نشده. هر نقض باقی‌مانده باید معیار موفقیت و دلیل مشخص داشته باشد.
2. آزمون دستی صفحه‌کلید: ترتیب منطقی، فوکوس قابل دیدن (SC 2.4.7 و 2.4.11)، trap و بازگرداندن فوکوس در دیالوگ‌ها، Escape، و skip link.
3. reflow در ۳۲۰ پیکسل CSS (SC 1.4.10)، zoom ۲۰۰٪، و کنتراست متن واقعی رندرشده در هر دو تم (SC 1.4.3).
4. `lang` و `dir` برای هر نسخه و برای بخش‌های زبان مخلوط درست باشد (SC 3.1.1 و 3.1.2)، و `<title>` به زبان همان نسخه باشد.
5. برابری معنایی دو زبان در محدودیت‌ها، خطاها و برچسب‌های منشأ.
6. برچسب‌های «WCAG AA/AAA» فقط دربارهٔ نسبت کنتراست یک جفت رنگ باشند و به‌عنوان انطباق برنامه ارائه نشوند.

**محدودکننده**
- آزمون با دست‌کم یک صفحه‌خوان (مثلاً NVDA با Firefox یا VoiceOver با Safari) و با کاربر فارسی‌زبان. اگر انجام نشده باشد، ادعا «بدون آزمون فناوری کمکی» باشد.
- مرورگرهای غیر از Chromium و دستگاه واقعی موبایل.
- خوانایی قلم فارسی (APCA برای Barlow تنظیم شده است).

## حکم ۴: بازتوزیع و انتشار

**الزامی**
1. هر دارایی انتشار از commit مشخصی قابل بازسازی باشد، یا دست‌کم تفاوت‌ها مستند باشند (CRLF، timestamp و ممیز شناور). manifest با فایل commit‌شده بخواند و CI این را کنترل کند (MSR-REL-001).
2. `pack:studio` روی checkout تمیز پاس شود، یا مراحل لازم مستند باشند.
3. محتوای ZIP یا tarball منتشرشده با متن جاری تناقض ادعایی نداشته باشد، یا اصلاحیهٔ عمومی کنار دارایی باشد (MSR-REL-002).
4. فهرست کامل مجوز هر جزء که واقعاً توزیع می‌شود (npm، HTML و ZIP) با اطلاعیهٔ لازم، از جمله انتساب CC BY 4.0 برای Font Awesome.
5. پرسش‌های باز مجوز (سازگاری AGPL-3.0 برای colorparsley، و شرایط APCA-W3 Limited License برای استفادهٔ غیر W3C) یا حل شده باشند، یا نظر مکتوب مشاور حقوقی داشته باشند، یا جزء ناسازگار حذف یا جایگزین شده باشد. **ممیزی نظر حقوقی نمی‌دهد.**
6. `author`، دارندهٔ حق نشر، `repository` و `bugs` واقعی باشند و گروه یا نهاد ساختگی در آن‌ها نباشد.
7. CI با دسترسی کمینه اجرا شود و actionها با SHA پین شده باشند. قالب release هم پیش از فعال‌شدن همین وضعیت را داشته باشد.
8. هیچ دادهٔ شخصی یا مسیر محلی در دارایی‌های عمومی نباشد (`walkthrough.md` و `review-2026-09-21.md`).
